# React Advanced Odontogram

## Critical Defaults
- This is a **standalone React library** — it must work independently of DentalQuoteCreator
- Never introduce DentalQuoteCreator-specific dependencies or imports
- Preserve the public API (`OdontogramShell` props interface)
- All changes must maintain backward compatibility with existing integrations

## Architecture
- **React 18.3** + **TypeScript 5.5** — single-page interactive dental charting component
- **Vite 7.3** — dev server and library build
- **Tailwind CSS** — utility-first styling with custom theme via CSS variables (`--odon-*`)
- SVG-based tooth rendering with per-surface interaction

## Key Files
- `src/App.tsx` — main `OdontogramShell` component (exported as default)
- `src/odontogram.ts` — core odontogram state logic and types
- `src/plugin.ts` — plugin system for extending functionality
- `src/status_extras.ts` — additional dental status types (bridges, implants, etc.)
- `src/theme.ts` — theme configuration and CSS variable mapping
- `src/i18n/translations.ts` — multilingual labels (HU, EN, DE, ES)
- `src/utils/numbering.ts` — tooth numbering systems (FDI, Universal, Palmer)
- `src/assets/teeth-svgs/` — SVG templates for individual teeth (11-48)
- `src/assets/icon-svgs/` — UI icons

## Tooth State Model
Each tooth has:
- `toothSelection`: tooth-base | missing | implant | pontic
- `toothSubstrate`: natural | radix | broken | crownprep
- `restorationType`: none | crown | inlay | onlay | veneer | bridge (implant-gated crowns/bridges compose with an implant connector layer). Restoration options are gated by tooth kind via `restorationOptions()` (`src/registry/restorations.ts`): an implant tooth offers only crown/bridge, plus the five `prosthesis` attachment entries; a missing/gap tooth (`toothSelection === "none"`) offers only a bridge pontic, plus the two removable-denture `prosthesis` entries; a `radix` substrate hides the restoration control entirely (`restorationRowHidden()` in `src/odontogram.ts`) — no restoration can be authored on a root remnant. A `bridge` restoration renders both the crown cap AND the saddle-connector layer via `composeRestorationLayers()`; the multi-tooth bridge-span overlay connector is arch-aware (mirrored saddle-Y fraction for the lower arch, `SADDLE_Y_FRACTION_LOWER` in `src/bridgeOverlay.ts`), and applying a bridge via a Statuses preset explicitly re-triggers the overlay recompute
- `restorationMaterial`: none | emax | gold | gradia | zircon | metal | metal-ceramic | telescope | temporary
- `prosthesis`: none | healing-abutment | locator | locator-denture | bar | bar-denture | removable-partial | removable-full — orthogonal implant-attachment / removable-denture axis, surfaced as "Kivehető:" entries in the combined restoration dropdown (gated per tooth kind — see `restorationType` above)
- `crownLeakage`: boolean — marginal-leakage finding, shown only when `restorationType` is crown or bridge. Both the tooltip (`getStateSummary`) and whole-mouth summary (`getOdontogramSummary`) gate this line on the exact same predicate as the `#crownLeakageRow` control (`!restorationRowHidden(state)` AND crown/bridge), so a tooth with a stale crown/bridge payload but a hidden restoration row (radix/milktooth/extraction/under-gum) never shows a leakage line the control itself doesn't display
- `endo`: none | endo-medical-filling | endo-filling | endo-filling-incomplete | endo-glass-pin | endo-metal-pin — mutually exclusive with `pulpDx`; both are surfaced through one merged "Pulp / Endo status" selector (vital vs. treated groups), and setting `endo` to a treated value normalizes `pulpDx` to `normal` (suppressing the diseased-pulp glyph)
- `pulpDx`: normal | reversible-pulpitis | irreversible-pulpitis | necrosis — AAE pulp diagnosis (replaced the retired `pulpInflam` boolean); mutually exclusive with `endo` (see above); `reversible-pulpitis` renders a reduced pulp glyph
- `pulpLatin`: none | pulpa-sana | hyperaemia-pulpae | pulpitis-acuta-serosa | pulpitis-acuta-purulenta | pulpitis-chronica-clausa | pulpitis-chronica-ulcerosa | pulpitis-chronica-hyperplastica | necrosis-pulpae | gangraena-pulpae — practical-Latin pulp subtypes, surfaced by the pulp picker only when the `pulpDetailLevel` setting (`simple` | `aae` | `latin`, default `aae`) is `latin`. `setPulpDetailLevel()` calls `notifyStateChange()`, so switching the level live-refreshes the whole-mouth summary and every tooth's tooltip immediately instead of staying stale until the next tooth edit
- `apicalDx`: normal | symptomatic-apical-periodontitis | asymptomatic-apical-periodontitis | acute-apical-abscess | chronic-apical-abscess | condensing-osteitis — drives the periapical glyph directly, decoupled from the `mods.inflammation` modifier. The `mods.inflammation` toggle (`syncInflammationModVisibility()` in `src/odontogram.ts`) is shown ONLY for missing (`toothSelection === "none"`) and extraction-socket (`no-tooth-after-extraction`) teeth — it is hidden on present teeth (where `apicalDx` drives the glyph) and on implants (where `periImplant` drives it instead)
- `periapicalType`: none | granuloma | cyst — periapical lesion subtype qualifying the `apicalDx` glyph, offered by the picker only under symptomatic/asymptomatic apical periodontitis; the legacy `abscess` value is still accepted/stored (folded into `apicalDx` on import) but no longer authorable, since it duplicates the apical diagnosis
- `resorptionType`: none | internal | external-cervical — replaced the retired `rootResorption` boolean
- `periImplant`: none | mucositis | peri-implantitis-mild | peri-implantitis-moderate | peri-implantitis-severe — implant-only peri-implant status (2018 World Workshop staging); `mucositis` reuses the existing periodontal gum glyph, `peri-implantitis-*` additionally activates the `peri-implant-bone-loss` layer at severity-scaled opacity (0.4/0.7/1.0); retires the implant `mods.inflammation` periapical glyph (missing/extraction-socket teeth are unaffected) and hides the inflammation/parodontal modifier checkboxes on implants
- `mods.mobility` (M1/M2/M3 grades): the mobility control is hidden/disabled on implant teeth (`mobilityRowHidden()`/`mobilityDisabled()` in `src/odontogram.ts`) — implants don't carry periodontal mobility
- `caries`: array of surface identifiers (mesial, occlusal, distal, buccal, lingual)
- `fillingSurfaces`: array of filled surfaces
- `rootCaries`: none | active | arrested | active-cavitated — wires the `caries-root` artwork layer on a present tooth, at an opacity driven by severity (`active` 0.5 / `arrested` 0.7 / `active-cavitated` full)
- `caries`/`fillingSurfaceMaterials`/`cariesSeverity`: caries is a per-surface **state machine**, not two independent fields. `cariesSeverity` (0-6) is the single unified per-surface severity — replacing the old separate `cariesDepths` (ICDAS) and `secondaryCaries` (CARS) fields. A surface in `caries` with **no** filling on it renders as primary caries (`caries-{surface}`, ICDAS-tiered opacity from `cariesSeverity`); the same surface **with** a filling present renders as recurrent caries instead (`subcaries-{surface}`, CARS-scored opacity from `cariesSeverity`) — a surface is never both at once. A contextual popup shows only the severity group relevant to the surface's current state (primary ICDAS-depth group when unfilled, CARS group when filled)
- `radiographicDepth`: per-surface none | E1 | E2 | D1 | D2 | D3 — radiographic caries depth, independent of the visual ICDAS/CARS severity scale (`cariesSeverity`); surfaced as a `data-radio` badge attribute
- `fillingDefect`: per-surface none | marginal | fracture | wear — filling-defect finding on a DIRECT restoration (marginal defect/overhang, fracture/chip, or worn/deficient material), independent of recurrent caries; gated to surfaces present in `fillingSurfaceMaterials` (only a filled surface can carry a defect). Authored via a left-side per-surface indicator on the Fillings card (mirrors the right-side caries-depth indicator); renders on the chart by activating the existing `defect-{surface}` artwork layer; shown in the tooltip and the whole-mouth fillings summary, labeled explicitly (`fillingDefect.label` prefix) the same way recurrent caries is labeled on the Caries summary line. Payload version 2.7
- `wearEdge`: none | attrition | erosion — incisal/occlusal tooth-wear type; `wearCervical`: none | abrasion | abfraction | erosion — cervical tooth-wear type. Replaced the two on/off bruxism-wear flags (`bruxismWear`/`bruxismNeckWear`); authored via two dropdowns on the wear row. Render the existing `tooth-bruxism-wear`/`tooth-bruxism-neck-wear` layers (no new SVG), gated on `toothSelection === "tooth-base"` + `restorationType === "none"` + `toothSubstrate === "natural"`. Shown in the tooltip and a dedicated whole-mouth "Wear" summary section. Payload version 2.8; a legacy edge-wear flag migrates to `attrition`, a legacy cervical-wear flag migrates to `abrasion`
- `discoloration`: none | tetracycline | fluorosis | nonvital | extrinsic | other — per-tooth discoloration cause. Tints the shown natural crown's fill (`tooth-base` or `milktooth-base`, whichever is active) a cause-specific colour at render time; gated on a natural, unrestored tooth-base or milk tooth (`toothSelection` tooth-base or milktooth + `restorationType === "none"` + `toothSubstrate === "natural"`). Fill is not part of the SVG-fingerprint parity check (only id/opacity/class are), so the tint is parity-safe. Shown in the tooltip and a dedicated whole-mouth "Discoloration" summary section. Payload version 2.9; additive, no migration needed
- `orthoAppliance`: none | bracket | band; `orthoDrift`: none | mesial | distal; `orthoVertical`: none | extrusion | intrusion (extrusion renders an arrow-up glyph, intrusion an arrow-down glyph); `orthoRotation`: boolean — per-tooth orthodontic charting axes. Reuse the dormant v2.5.0 ortho artwork (no new SVG); gated on a present natural tooth (`toothSelection` tooth-base or milktooth — the shared `orthoAllowed` predicate). Shown on the chart, in the tooltip, and a new whole-mouth "Orthodontics" summary section. Payload version 2.10; additive, no migration needed
- Wear (`wearEdge`/`wearCervical`) and `discoloration` each have an app-level session detail level (`ToothDetailLevel`: `simple` | `complex`, default `complex`), set via Settings → Tooth details. Simple mode swaps the type/cause dropdown for a yes/no toggle per finding (wear on → `attrition`/`abrasion`, discoloration on → `other`); complex mode (default) shows the full dropdown. The setting only toggles which control is visible/derives its checked state from the stored value — it never mutates `state`, so the stored value survives switching levels. No payload/render/FHIR change.
- `SurfaceNotation`: `simple` | `full` (default `full`) — app-level session setting (`getSurfaceNotation`/`setSurfaceNotation` in `src/odontogram.ts`), set via Settings → Tooth details → "Surface notation". Drives `surfaceLetter()`/`surfaceLabelKey()`, which resolve the DISPLAY letter/caption for a caries/filling surface given the tooth's arch (`isUpperTooth`) and anterior/posterior position (`isAnteriorTooth`); shared by the whole-mouth summary AND both the caries and filling-defect surface pickers (letter + caption). Mapping — FULL: occlusal → "I"/incisal on an anterior tooth (else "O"/occlusal); buccal → "L"/labial on an anterior tooth (else "B"/buccal); lingual → "P"/palatal on an upper tooth (else "L"/lingual — a lower-anterior tooth therefore shows "L" for both buccal and lingual, disambiguated by cross-position + caption); mesial → "M", distal → "D", subcrown → "SC" (unaffected by the setting). SIMPLE: always the tooth-independent B/M/O/D/L/SC set. The stored `surface` key (e.g. `"occlusal"`, `"buccal"`, `"lingual"`) is never affected — only the displayed letter/label changes.
- Settings → "Panels" tab (`settings.panels.*`; `showStatusCard`/`onShowStatusCard`, `showOrthoCard`/`onShowOrthoCard` in `App.tsx`): independently toggles whether the whole-mouth Statuses card and Orthodontics card render (both default visible). Session-level UI state only — no payload/render/FHIR change to per-tooth data.
- Settings tabs are `general | panels | toothDetails | caries | pulpa | notes` (`SETTINGS_TABS` in `src/SettingsModal.tsx`). The former separate "Secondary caries" tab is merged into the "Caries" tab, with the CARS (secondary-caries) control positioned directly above Radiographic depth.
- `extractionPlan`, `crownNeeded`, `crownReplace`: boolean flags
- The per-tooth tooltip (`getStateSummary`) and the whole-mouth summary panel (`getOdontogramSummary`) surface all clinical axes above — pulp/apical diagnosis (+ lesion subtype), root resorption, peri-implant status, graded root caries, calculus, crown marginal leakage, fracture, contact loss, and typed edge/cervical wear — not just what is drawn on the chart. The panel groups pulp/apical/resorption/peri-implant findings into a dedicated `diagnoses` summary section, adds a dedicated `wear` summary section, and caries surfaces a coarse severity qualifier (superficial/moderate/deep) alongside the per-surface state.

## Periodontal Data (perio sub-record)
- Each tooth state carries a `perio` sub-record — `{ pd: Map<site,mm>, gm: Map<site,mm>, bop: Set<site>, sup: Set<site> }` over the six standard sites `PERIO_SITES = ["MB","B","DB","ML","L","DL"]` (buccal row, then lingual row). Kept SEPARATE from the 5-surface caries maps (different site convention). First sub-project (P1) of the periodontal-parameters arc; later sub-projects add the perio-chart grid UI, SVG recession/furcation rendering, and 2017 staging/grading.
- **Semantics:** absence = "not charted", NOT zero. A site is charted once its `pd` is set; `gm` (gingival margin vs CEJ, SIGNED: recession +, coronal/pseudopocket −) defaults to 0 when `pd` is set but `gm` unset. `setPerioSite(toothNo, site, {pd?,gm?,bop?,sup?})` validates + clamps (pd int 1–15, gm int −10…+20); `pd` null/`<1` un-charts the site (atomically clears pd/gm/bop/sup for it — no orphans).
- **Derived, never stored:** `CAL = pd + (gm ?? 0)` (`getToothCal`); recession = `max(gm,0)`; pseudopocket = `max(−gm,0)`; whole-mouth `%BOP = (charted sites ∩ bop) ÷ charted sites` (can't exceed 100 — BOP on an un-charted site is ignored). `getPerioSummary()` returns charted/bleeding counts, %BOP, worst CAL, max PD. Public API: `setPerioSite`/`getToothPerio`/`getToothCal`/`getPerioSummary`/`getPerioChart`. `getPerioChart`/`getToothPerio` are OMIT-WHEN-EMPTY (uncharted sites have no key — default them like `radiographicDepth`).
- Payload version **2.12** (additive; `perio` omitted from a tooth's serialized record when no site is charted, so a no-perio case is byte-identical apart from the version). Dual-state aware (lives on the tooth state → participates in status/plan charts + the R2-B `getPlanChanges()` diff via one summary-level `perio` DIFF_AXES entry). No SVG render yet (that's a later sub-project) → SVG-fingerprint parity byte-identical.
- **Graphical perio chart (`src/PerioChart.tsx` + `src/perioGraphic.ts`):** the perio chart is drawn like a real perio chart — the teeth in a continuous **occlusal-to-occlusal** arch (upper crowns down, lower up; per-arch `archOrientTransform` flip about the CEJ baseline, curves + mm grid ride the same oriented row groups so they align), reusing the existing artwork, with a CEJ line + a **numbered mm guide grid** (`buildMmGridLayer`, lines at `ROW_BASELINE_Y + n·PERIO_MM_PX`, behind teeth, aria-hidden) + a pocket/margin curve over them, number rows in aligned columns, and a summary. The arch SVG is **responsive** (no fixed width/height — `viewBox` + `width:100%`; the number grid keeps fixed-px columns so a narrow window scrolls). **Implant teeth** render the template's `#implant-base` layer instead of `#tooth-base` (`getToothBaseGroupFromCache(..., {implant})` + a per-template `IMPLANT_CEJ_Y` anchor; `isToothImplant` reads the active chart). Furcation/plaque status→plan changes surface in the R2-B "What changes" diff (summary-level `DIFF_AXES` entries). `src/perioGraphic.ts` holds the DOM-free logic: `getToothBaseGroup(toothNo)` extracts ONLY the `#tooth-base` layer from a tooth's template (its OWN independent template cache — separate `fetch`+`DOMParser`, architecturally disjoint from the live grid's `tplCache`, so it can never corrupt the real chart; clones before transforming; drops `gum-base`/`bone-base`/`tooth-healthy-pulp`/`tooth-base-beauty`/`milktooth-base`), applies per-position size (FDI last digit 2→80% width, 3→taller root, rest as-is) + a horizontal mirror equal to the live grid's NET flip (`mirror XOR rot180` — every lower-arch tooth carries `rot:180`, whose horizontal half cancels or adds to `mirror`), aligned on a common **CEJ baseline** via per-template `CEJ_Y` anchors (measured from `gum-base`'s coronal edge as a cervical proxy); the palatal row is the buccal row wrapped in a vertical mirror. `perioCurve(sites, {cejY, mmPx, siteX})` is a pure helper → `marginY = cejY + gm*mmPx`, `pocketY = marginY + pd*mmPx`, `null` for uncharted (line gaps); the overlay draws the red CEJ line + margin/pocket polylines + a filled band, reusing the SAME `archToothLayout` per-tooth x/width so it tracks the teeth. Live + dual-state via `onStateChange`.
- **Cairo recession + CEJ/root-concavity (PG-C):** `getToothRecessionType(toothNo)` derives the Cairo type (`none`/`rt1`/`rt2`/`rt3`) from `getToothCal` — only when the buccal margin `gm.B > 0`, comparing `max(CAL[MB],CAL[DB])` (interproximal) vs `CAL[B]` (buccal): RT1 interprox <1mm, RT2 interprox ≤ buccal, RT3 interprox > buccal (pure, no storage; surfaced as the `"cairo"` overlay layer + tooltip/summary). `cejVisibility` (`none`/`detectable`/`not-detectable`) and `rootConcavity` (`none`/`mild`/`deep`) are per-tooth **registry enum axes** (`registry/axes.ts` + `fieldMappings.ts` 1:1 + `codesystems.ts` local codes; NO `svgLayer` → no odontogram render → parity byte-identical); gated setters `setCejVisibility`/`setRootConcavity` (through the DS-1 gate), omit-when-`none` serialize, payload **2.14**, FHIR via the declarative axis path, Dental Chart cycle-button rows + info popups + summary/tooltip.
- **Graded indices + mucogingival findings (PG-D):** five additional per-tooth axes. **PI** (`getPlaqueIndex`/`setPlaqueIndex`) and **GI** (`getGingivalIndex`/`setGingivalIndex`) — Silness-Löe Plaque Index / Löe-Silness Gingival Index, per-surface graded `0`-`3` over the same 4 O'Leary surfaces as `plaque` (mesial/distal/buccal/lingual), stored as `pi`/`gi` `Map<surface,grade>` (grade `0` clears the entry — never distinct from "never charted", same "absence = not charted" convention as every other graded axis). **KG** (`getKeratinizedWidth`/`setKeratinizedWidth`) — keratinized gingiva width, a single per-tooth BUCCAL mm scalar (integer, clamped 0-15 via `clampKg()`; `null` = not charted, never a stored 0), deliberately NOT per-site/per-surface unlike PI/GI or the 6-site perio-probing record. **GT** (`getGingivalThickness`/`setGingivalThickness`, `gingivalThickness` field, `VALID_GINGIVAL_THICKNESS`) — gingival thickness phenotype (`unknown`/`thin`/`medium`/`thick`, default `unknown`) and **Miller class** (`getMillerClass`/`setMillerClass`, `millerClass` field, `VALID_MILLER_CLASS`) — Miller recession classification (`none`/`i`/`ii`/`iii`/`iv`, default `none`) are per-tooth **registry enum axes** (`registry/axes.ts` + `fieldMappings.ts` 1:1 + `codesystems.ts`, mirroring `cejVisibility`/`rootConcavity`'s PG-C pattern exactly). All five interactive setters route through the DS-1 gate (`gateToothEdit`); NONE has an `svgLayer` → no odontogram render → parity byte-identical. PI/GI/KG serialize to FHIR via a bespoke path (`src/fhir/toFhirPerio.ts`, engine-local codes — no dedicated LOINC, same treatment as per-site BOP/plaque) as additional components on the existing per-tooth periodontal-panel `Observation`; GT/Miller serialize via the declarative axis path like `cejVisibility`/`rootConcavity`. Payload **2.15**, Dental Chart rows (PI/GI heat-bucketed like the mm ramps; KG/GT/Miller cycle-button/value rows) + info popups + tooltip/summary.
- **Peri-implant Mombelli indices (PG-E):** two implant-only per-surface graded axes. **mPI** (`getPeriImplantPlaque`/`setPeriImplantPlaque`) and **mBI** (`getPeriImplantBleeding`/`setPeriImplantBleeding`) — Mombelli modified Plaque Index / modified Sulcus Bleeding Index, per-surface graded `0`-`3` over the same 4 surfaces as PI/GI (mesial/distal/buccal/lingual), stored as `mpi`/`mbi` `Map<surface,grade>` sharing the same `setSurfaceGrade`/`getSurfaceGrade` machinery as PI/GI (grade `0` = not charted, same convention). **Implant-gated end-to-end**: the setter no-ops on any tooth whose `toothSelection !== "implant"` (guard runs before the DS-1 gate, so a gated call marks nothing and fires no state-change notification), and the Dental Chart cell's `disabled` predicate is `readOnly || !isToothImplant(toothNo)` — a deliberate departure from the shared `isPerioRowHidden` gate every other perio row uses, since that gate hides implants (`isToothPresent` excludes them) exactly where mPI/mBI need to be active. Hydrate is intentionally NOT implant-gated (non-interactive path, same tolerance policy as every other axis) — only the setter enforces the gate. NEITHER axis has an `svgLayer` → no odontogram render → parity byte-identical. FHIR via the bespoke `src/fhir/toFhirPerio.ts` path (local codes `mod-plaque-index-mombelli`/`mod-bleeding-index-mombelli`, no dedicated LOINC — same treatment as PI/GI) as additional components on the existing per-tooth periodontal-panel `Observation`. Payload **2.16**. Also consolidates the Dental Chart overlay's whole-mouth read-out (`overlayReadout`) to cover `pi`/`gi`/`kg` in addition to `bop`/`plaque`/`mpi`/`mbi` — closing a PG-D-era gap where only bop/plaque had a read-out.
- **Case-level metadata object (P4a):** the engine's FIRST case-level object — a single shared block (type `CaseMeta` in `src/odontogram.ts`), NOT per-tooth and NOT dual-state (both `charts.status` and `charts.plan` payloads carry the same object), mirroring the top-level `globals` payload key. Carries patient **age** (`0`-`120`), **smoking status** (`unknown`/`never`/`former`/`current` + cigarettes/day `0`-`99`), **diabetes status** (`unknown`/`none`/`present` + HbA1c `3.0`-`20.0`, one decimal), and two perio-outcome summary stats: **teeth lost to periodontitis** (`0`-`32`) and **max radiographic bone loss %** (`0`-`100`). API: `getCaseMeta()`, `setCaseAge`/`setSmokingStatus`/`setCigarettesPerDay`/`setDiabetesStatus`/`setHba1c`/`setToothLossPerio`/`setMaxRblPercent`, `resetCaseMeta()` — all numeric setters clamp/no-op on non-finite input, `null` explicitly clears; enum setters validate against a fixed set and ignore invalid values. Serializes omit-when-empty to the payload's top-level `case` key (absent entirely when every field is at its default); hydrated via the shared `hydrateImportedCharts` data-path used by both `importStatus()` and the test seam. Wired into the reset-all path (blank-slate reset, like edentulous) alongside `__resetChartStateForTest`. Surfaced as a collapsible panel on the Dental Chart (`src/PerioChart.tsx`, shared `gridBody` so it renders in both `inline`/`popup` chrome) and as a compact labelled fragment appended to `getOdontogramSummary()`'s `periodontalText` (`caseContextSummaryFragment()`) whenever the case isn't empty — only actually-charted fields are mentioned. Payload **2.16 → 2.17** (additive). **No FHIR yet** — this is chart-independent case context only; the periodontal staging/grading classification (and its FHIR `Condition`/BNO mapping) is the P4b sequel. NEITHER a render axis nor per-tooth → SVG-fingerprint parity byte-identical.
- **2017 periodontal classification + first FHIR Condition (P4b):** completes the round-2 periodontal arc. A dependency-free pure derivation core (`src/perioClassification.ts`, `derivePerioClassification`) computes `diagnosis`/`stage`/`grade`/`extent` from an already-reduced `PerioDerivationInput` — per-tooth worst interdental/buccal-oral CAL + max PD, whole-mouth %BOP + max furcation, and the P4a `PerioMetaInput` (age/RBL%/tooth-loss/smoking/diabetes) — with NO imports from `odontogram.ts` and no `Date`/`Math.random`, so it is deterministic and callable from either live state or a serialized payload. Two thin adapters feed it: `buildDerivationInputFromState()` in `odontogram.ts` (live chart → UI) and a payload-side equivalent in `src/fhir/toFhirPerio.ts` (exported JSON → FHIR) — one-directional dependency, no duplicated derivation logic. Four per-axis clinician overrides live on `caseMeta` (`diagnosisOverride`/`stageOverride`/`gradeOverride`/`extentOverride`, each a valid enum value or `null`; NOT DS-1 gated, same treatment as the rest of `CaseMeta`) via `setDiagnosisOverride`/`setStageOverride`/`setGradeOverride`/`setExtentOverride`; `getPerioClassification()` returns the final per-axis value (override ?? derived) alongside the untouched `derived` result and a per-axis `overridden` flag, surfaced as a Dental Chart classification panel and a summary-line fragment. `appendPerioCondition` (`src/fhir/toFhirPerio.ts`) emits the engine's **FIRST FHIR `Condition`** — BNO/ICD-10 K05.3 (chronic periodontitis) / K05.2 (molar-incisor pattern, checked before the generic periodontitis code) / K05.1 (chronic gingivitis) — with type-differentiated `stage[]` entries (periodontal-stage/-grade/-extent, each only when that axis is applicable/non-indeterminate) and `evidence[]` referencing smoking-status and HbA1c Observations (emitted only when those case fields are charted); emits NOTHING for a "health" diagnosis. Payload **2.17 → 2.18** (additive — the four override fields). Neither the derivation nor the overrides have an `svgLayer` → SVG-fingerprint parity byte-identical. **Important:** this is the FIRST sub-project to touch the FHIR golden fixture, but the delta is empty — all four parity fixtures carry no perio/case data, so they derive `diagnosis: "health"` and `appendPerioCondition` emits nothing; a diseased case DOES emit a Condition (covered by `p4b-condition-fhir.test.ts`), it's just that none of the golden fixtures happen to be diseased.
- **Index switcher + overlays (PG-B):** a radio-style switcher (`#perioOverlaySwitch`) in the Dental Chart header sets a runtime `perioOverlayLayer` (`getPerioOverlayLayer`/`setPerioOverlayLayer`; default `"none"`) that repaints a highlight overlay on the teeth — `pd`/`cal`/`gr` heat ramps (`pdCalHeatBucket`/`recessionHeatBucket`, GR only `gm>0`), `bop` dots, `plaque` marks, `pd5`/`pd6` deep-pocket heat. All display-only over existing data (`getToothPerio`/`getToothCal`/`getPerioSummary`/`getToothPlaque`); the overlay `<g>` (aria-hidden) reuses the SAME `archToothLayout` + oriented row groups as the curve/mm-grid (one geometry), so highlights land on the right sites both arches. `%BOP`/`PI%` read-outs from `getPerioSummary`. ## Chart State Model (Status vs Plan)
- **Status→Plan edit propagation (DS-1):** a per-tooth runtime `Set planEditedTeeth` marks teeth explicitly edited while in Plan mode. ALL interactive tooth edits route through a central gate — `gateToothEdit(toothNo, applyFn)` (single) / `gateToothEditBatch(toothNos, applyFn)` (atomic over a set; `applyStatusExtra`/`applyToSelected`/`setEdentulous`/dentition presets use it). Logic: **plan mode** → `applyFn()` + mark the tooth; **status mode, tooth NOT plan-edited** (or plan uninitialized) → `applyFn()` + `mirrorStatusToPlan(toothNo)` (deep copy via serialize→hydrate) so the plan tracks the corrected reality and the tooth shows NO diff; **status mode, tooth IS plan-edited** → a **blocking in-app confirm** (`src/DualStateConfirm.tsx`, mirrors SettingsModal) BEFORE applying — accept applies to status only (plan stays → they diverge, the diff shows it), cancel applies nothing + reverts the control. Batches confirm ONCE over the whole set and apply all-or-none. `applyFn` returning `false` (no-op) skips marking/mirroring. `planEditedTeeth` is runtime-only (NOT serialized) and cleared on plan (re)init / reset / import / `setPlanChart`. NON-interactive paths (import/hydrate, reset/clear buttons, `cloneChart`, lazy `defaultState()` vivify) are NOT gated. Parity byte-identical (edit-routing only).
- Two parallel per-case states, `charts.status` and `charts.plan` (both `Map<toothNo, ToothState>`, declared as `const charts: Record<"status" | "plan", Map<...>>` in `src/odontogram.ts`). `toothState` is a module-scoped, REASSIGNABLE `let` alias pointing at whichever chart is currently active — every pre-existing `toothState.get/set/...` call site keeps operating on the active chart unchanged.
- `chartMode: "status" | "plan"` tracks the active chart (default `"status"`). `getChartMode()`/`setChartMode(mode)` are the public read/switch API; `setChartMode()` reassigns `toothState`, does a full repaint of every tooth (reusing the same repaint loop `importStatus()` uses — no new render path), and syncs the header toggle UI.
- The plan chart is lazily initialized: the FIRST time `setChartMode("plan")` is called, `charts.plan` is deep-copied from `charts.status` via the existing `serializeState → hydrateState` round-trip (`cloneChart()`), guaranteeing independent Maps/Sets so edits never leak between charts. Later switches reuse whatever is already in `charts.plan` — it is never re-cloned from status once initialized.
- UI: a `Status | Plan` segmented toggle (`#chartModeToggle`, buttons `#chartModeStatus`/`#chartModePlan`) sits in the dental-chart card header (`src/App.tsx`); the active chart also gets a `.plan-mode` class on the chart card as a visual cue when Plan is active.
- Per-state public API (independent of which chart is active): `getStatusChart()` / `getPlanChart()` return each chart's payload (`{version, globals, teeth}`); `setPlanChart(payload)` hydrates the plan chart only (status untouched), repainting the DOM only if plan is the currently active mode.
- Export/import stay status-primary: `exportStatus`/`exportFhir`/file import always target `charts.status` explicitly, never the active-chart alias — exporting while in Plan mode still yields the status chart. The JSON export gains an additive top-level `plan` field, emitted only when the plan chart is initialized AND differs from status; payload version bumped to **2.11** (imports still accept legacy 1.4–2.10). Import restores `plan` when present; its absence clears/uninitializes the plan chart (never resurrects a stale plan from before the import).
- FHIR export/import remain status-only — `buildFhirBundle()`/`parseFhirBundle()` are unaffected by the plan chart; there is no FHIR representation of the plan chart yet.
- Render is byte-identical to the pre-dual-state single chart (`parity.test.ts` SVG fingerprints) — the toggle only changes WHICH chart is drawn, never how a chart renders.
- **Proposed styling (plan-only render):** in Plan mode, any SVG layer active in the plan chart but NOT in the status chart for that tooth (a finding the plan *adds*) renders with a distinct dashed, tinted "proposed" outline. `applyProposedStyling(toothNo, svg)` runs in `applyStateToSvg`'s loop AFTER `applyStateToSvgSingle` (never inside it — it clones the svg and re-invokes `applyStateToSvgSingle` to render the status state, which would recurse): it computes `planIds ∖ statusIds` (status rendered into `svg.cloneNode(true)` via `applyStateToSvgSingle(toothNo, clone, charts.status.get(toothNo) ?? defaultState())`, then `collectActiveLayers`) and marks the plan-only layers via the **inline-style channel** (`style.strokeDasharray` + a `style.stroke` tint) — never `style.opacity` or a CSS class, the two channels `collectActiveLayers` fingerprints. Gated on `chartMode === "plan" && planInitialized`; `clearProposedStyling` runs first on every call and restores each captured `data-base-dash`/`data-base-pstroke` (symmetric reset, so switching back to Status or editing a plan finding to match status leaves no stray dashes). A `#proposedLegend` ("dashed = proposed") shows via pure CSS under the chart card's `.plan-mode` class. Status-mode render + parity capture never run this branch → byte-identical.
- **Status→Plan diff:** `getPlanChanges()` returns a pure, read-only diff of the two charts — `PlanChange[]` (`{ toothNo, axis, from, to }`), one entry per tooth per treatment axis whose human-readable label differs between `charts.status` and `charts.plan`; `[]` when the plan is uninitialized. It compares over `DIFF_AXES` (presence, substrate, restoration, prosthesis, crownAction, ortho, pulpEndo, apical), each described by the SAME label helper the tooltip/summary already use (no reinvented copy). The list is also exposed on `getOdontogramSummary()` as `plannedChanges`; `App.tsx` renders it as a distinct "What changes" box (`#plannedChangesBox`) under the Tooth-information panel, shown only when non-empty. No render/state/payload change (parity byte-identical).
